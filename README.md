# Aspia Configurator

Веб-сервис для Debian/Ubuntu: выбираете MSI-пакет Aspia Host, заполняете (или импортируете и правите) форму настроек —
получаете пакет, который при установке кладёт собранный файл во временный каталог и штатным действием пакета
`ImportSettings` импортирует именно его (`aspia_host.exe --import="[TempFolder]<файл>" --silent`), вместо файла
настроек по умолчанию.

Сервис не добавляет в пакет никакой новой логики запуска — он только переключает уже существующий, авторский
custom action пакета на другой файл. Поэтому он работает исключительно с пакетами Aspia Host, где такой custom
action уже есть; на любом другом MSI сборка отклоняется.

## Установка

Склонируйте репозиторий на сервер и выполните `install.sh`:

```bash
git clone https://github.com/bolgov0zero/Aspia-Configurator.git
cd Aspia-Configurator
sudo ./install.sh
```

Скрипт ставит `gcab`, `python3-flask`, `gunicorn` и инструменты сборки, **собирает msitools с исправлением** (1–2 минуты, см. ниже),
создаёт пользователя `msirb`, копирует приложение в `/opt/msi-rebuilder`, регистрирует сервис `msi-rebuilder` в systemd
(автозапуск при загрузке) и в конце печатает адрес. Нужен доступ к репозиториям apt.

**По умолчанию сервис открыт без пароля** — заходить и собирать пакеты может кто угодно, у кого есть сетевой доступ
к порту. Это рассчитано на закрытую сеть/VPN, снаружи которой стоит TLS (например, nginx/Caddy как reverse proxy)
и файрвол. Если нужна парольная защита — `--password ПАРОЛЬ` или `--reset-password` (сгенерирует случайный и
покажет один раз); `--no-password` возвращает уже защищённый сервис обратно к открытому доступу.

Остальные параметры (все необязательные): `--port 8080`, `--host 0.0.0.0`, `--user admin`.
Повторный запуск обновляет код и перезапускает сервис, настройки сохраняются.

## Использование

Открыть `http://<сервер>:8080/` — форма состоит из двух частей.

**Исходный пакет.** Либо загрузить .msi вручную, либо переключиться на «С GitHub (3.x)» и выбрать версию из
списка — сервис сам скачает Windows x64 MSI-ассет (`aspia-host-<версия>-x86_64.msi`) нужного релиза с
`github.com/dchapyshev/aspia/releases` и сверит его контрольную сумму с той, что прислал GitHub. Список версий
обновляется с сервера не чаще раза в 10 минут. Пакет должен содержать штатное действие `ImportSettings`; если
его нет, сборка отклоняется.

**Конфигурация.** Единая форма с настройками хоста, изначально заполненная реальными дефолтами свежеустановленной
программы. Можно править поля прямо в ней, а можно сначала нажать «Импортировать существующий файл настроек» —
JSON разбирается прямо в браузере и подставляет свои значения в форму (поля, которых в файле нет, остаются
дефолтными). Пароли восстановить из файла нельзя, поэтому:

- у пользователей, пришедших из файла и не тронутых в форме, стоит пометка «пароль из файла» — их SRP-запись
  переносится в новый файл как есть, без пароля; чтобы сменить пароль конкретному пользователю, откройте его
  карточку и снимите галочку «Пароль из файла — не менять»;
- то же для пароля защиты настроек, если он был включён в исходном файле.

В файл настроек, который в итоге вшивается в пакет, попадает только то, что отличается от дефолтов программы —
остальное и так верно после обычной установки.

**Ничего из этого нигде не сохраняется** — ни исходный пакет, ни файл настроек, ни результат: всё обрабатывается во
временном каталоге на время одного запроса и удаляется сразу после того, как ответ (файл) полностью сформирован —
ещё до того, как он дойдёт до браузера. На сервере в принципе нет списка пакетов или истории сборок: страница ничего
не помнит между запросами, и перезагрузка/повторный визит показывает ровно то же самое пустое состояние. Один
человек не увидит файлы другого.

Обратная сторона: исходный MSI-пакет (обычно 15–20 МБ) нужно выбирать заново при каждой сборке — сервис
сознательно не хранит его между запросами, даже общим для всех шаблоном.

В шапке страницы виден только общий счётчик «Пакетов собрано» — сколько раз через сервис успешно собрали пакет.
Это просто число (`/var/lib/msi-rebuilder/build_count`), без привязки к тому, кто и что именно собирал.

## Что происходит с пакетом

- файл кладётся в `TempFolder` (`%TEMP%` на целевой машине) отдельным компонентом, привязанным к тем же функциям
  (Feature), что и сам `aspia_host.exe` — то есть ставится ровно тогда, когда ставится и сам хост;
- у существующей строки `ImportSettings` в таблице `CustomAction` меняется только путь к файлу в кавычках
  (`--import="[SourceDir]aspia-host.json"` → `--import="[TempFolder]<загруженный файл>"`); тип действия и вся
  остальная команда (например, `--silent`) не трогаются;
- файл упаковывается в **отдельный** встроенный cab-архив — оригинальные данные пакета не перепаковываются;
- прописывается `MsiFileHash`, чтобы установщик перезаписывал файл, если на диске лежит другая версия;
- по желанию (галочка «Удалять файл штатным RemoveFile», включена по умолчанию) добавляется строка `RemoveFile`:
  файл удаляется штатным механизмом MSI при удалении программы и перед установкой новой копии поверх старой.
  Сразу после самого импорта в этой же установке файл не удаляется — по порядку установки `RemoveFiles`
  выполняется раньше `ImportSettings`, и штатными средствами MSI это не обойти без нового отдельного действия,
  которое сервис сознательно не добавляет;
- всё остальное в пакете остаётся **байт-в-байт как в оригинале** (остальные таблицы, основной cab, иконки,
  языковые transforms). PackageCode по умолчанию не меняется (галочка «Сменить PackageCode» включает смену);
- **цифровая подпись удаляется** — после правки она всё равно недействительна. Если нужна подпись, подпишите
  готовый пакет своим сертификатом (`signtool`).

Ограничения: пакет обязан содержать действие `ImportSettings` вида `--import="[Каталог]файл" ...` — иначе сборка
отклоняется; если в пакете уже есть файл с таким именем в Temp, сборка тоже отклоняется; лимит размера файла — 2 ГБ
(ограничение MSI). ProductCode и версия остаются прежними: чтобы поставить изменённый пакет поверх уже
установленного такого же, удалите старый или задайте новую версию в исходном пакете.

## Почему msitools собирается из исходников

Штатный `msibuild` (msitools 0.106, в т.ч. Debian 13) портит реальные пакеты вроде Aspia — у них внутри лежат 22 языковых
transform'а. Три проблемы `libmsi`, все исправлены патчем `vendor/msitools-storage-fixes.patch`:

1. Падение при сохранении: `Attempt to wrap an output that is already wrapped / failed to save storages`. При копировании storages
   выходные потоки не закрываются, и libgsf падает на втором потоке ≥ 4 КБ.
2. Тихая порча: пересохранённые storages теряют CLSID (у transform'ов `{000C1082-0000-0000-C000-000000000046}`), и Windows Installer при
   установке выдаёт «Ошибка применения преобразований» (1624).
3. Строки таблиц пишутся не по порядку первичного ключа (Windows Installer хранит их отсортированными по ID строк). Если новый ключ
   получает переиспользованный освободившийся ID строки, строка окажется не на своём месте, и установка падает с ошибкой 2211
   «Could not create database table Directory». Патч сортирует строки при сохранении таблицы.

Исходники msitools лежат в `vendor/`, `scripts/build-msitools.sh` применяет патч и ставит результат в `/opt/msi-rebuilder/msitools`.
Сервис использует именно эти `msibuild`/`msiinfo` (переменная `MSIRB_MSITOOLS_DIR`), системный msitools не затрагивается.
Повторный запуск `install.sh` пересобирает только при изменении патча.

## Настройки

`/etc/msi-rebuilder/msi-rebuilder.env` (после правки — `sudo systemctl restart msi-rebuilder`):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `MSIRB_HOST`, `MSIRB_PORT` | `0.0.0.0`, `8080` | где слушать |
| `MSIRB_USER`, `MSIRB_PASSWORD` | `admin`, пусто | доступ к интерфейсу; пустой пароль = без авторизации |
| `MSIRB_MAX_UPLOAD_MB` | `1024` | лимит загрузки |
| `MSIRB_MSITOOLS_DIR` | `/opt/msi-rebuilder/msitools` | каталог с пропатченным msitools |

Управление: `systemctl status|restart msi-rebuilder`, журнал: `journalctl -u msi-rebuilder -f`.

## Безопасность

По умолчанию сервис открыт без пароля — доступ ограничивается сетью (закрытый сегмент/VPN) и TLS снаружи (reverse
proxy), а не самим приложением. Для варианта «С GitHub» сервису нужен исходящий HTTPS-доступ к `api.github.com` и
`github.com` (или его CDN релизов) — если сеть сервера закрыта наружу полностью, останется только ручная загрузка
файла. Загружаемый файл настроек, судя по содержимому, секретный (`password_hash`,
`router_public_key`, `seed_key`) — но он не сохраняется на сервере и передаётся только на время одной сборки,
поэтому главное — не открывать порт в интернет и держать TLS между браузером и сервисом.

Если нужна ещё и парольная защита поверх сети — `sudo ./install.sh --reset-password` (см. «Установка»).

Сервис умышленно не даёт вписать в пакет запуск произвольной команды: он только меняет путь к файлу в уже
существующем, авторском `ImportSettings` пакета Aspia Host, и отказывается работать с пакетами, где такого
действия нет или оно имеет неожиданный вид.

## Удаление

```bash
sudo ./uninstall.sh          # сервис удалить, данные оставить
sudo ./uninstall.sh --purge  # удалить и данные с настройками
```
